# 隐含信用利差 GPU 实施状态

> 状态更新（2026-08-30）：CPU/CUDA 双后端、连续数组预处理、GPU
> 二分求根、CPU/GPU 一致性测试和最终缓存原子替换已经落地。本文保留原设计
> 作为实现记录；常规周更新只处理 Manifest 截止日之后的增量数据。

## 目标与边界

- 将 `market_data_contracts.py::build_implied_credit_spread_matrix()` 从逐债券、逐交易日的 Python/Scipy 串行求解，改为适配本机 NVIDIA GeForce RTX 5060 Laptop GPU 的批量 CUDA 求解。
- 保持现有金融定义不变：契约现金流、实际天数/365、国债曲线的时点约束与 7 天陈旧度上限、非负信用利差、5.0 上限及无解规则均不改变。
- 输出仍为与 `maturity` 同索引、同列的 `DataFrame`，并继续写入 `cb_credit_spread_cache.csv`。
- 保留 CPU 实现作为基准和回退路径。
- 已安装并验证 `numba==0.62.1` 与 CUDA 运行时；日常更新不运行全量数据管线。

## 改造前瓶颈

当前实现对约 `2320 × 954` 个债券日期单元执行 Python 双层循环。每个有效单元还会：

1. 重建未来契约现金流；
2. 多次查询并插值历史国债曲线；
3. 使用 Scipy `brentq` 反解利差。

这导致 GPU 在信用利差阶段完全闲置，而且函数返回前没有中间检查点。本次运行在约 63 分钟 CPU 后暂停，尚未生成新的信用利差缓存。

## 推荐技术方案

采用“CPU 一次性预处理 + Numba CUDA 批量二分求根 + CPU 回填结果”的混合架构。

选择 Numba CUDA 的原因：

- 当前环境已有 `numba 0.62.1`，`cuda.is_available()` 为真；
- 本机 RTX 5060 Laptop GPU 可识别，8 GB 显存，Compute Capability 12.0；
- 仓库的 ZL 生产模型已经使用 `numba.cuda`，无需引入第二套 GPU 技术栈；
- CuPy 当前未安装；PyTorch 虽已安装，但不适合本任务的变长契约现金流和逐问题状态码。

GPU 不直接处理 Pandas、日期、字符串或 Scipy。CPU 先把所有有效问题压平成连续数值数组；GPU 每个线程处理一个债券日期问题，使用固定次数的双精度二分法求根。

### GPU 输入布局

- `observed_value[n]`：观测纯债价值；
- `cashflow_offsets[n + 1]`：CSR 风格的变长现金流边界；
- `cashflow_times[m]`；
- `cashflow_amounts[m]`；
- `risk_free_rates[m]`；
- `row_positions[n]`、`column_positions[n]`：用于回填矩阵；
- `status[n]`：成功、零利差、输入无效、超过上界等状态码。

### 数值求解

每个 CUDA 线程：

1. 计算 `PV(0)`，应用现有的 `max(1e-8, PV(0) * 1e-8)` 容差；
2. 检查观测价值高于无风险价值、零利差和 `PV(5.0)` 仍高于观测价值等现有边界；
3. 在 `[0, 5.0]` 上执行固定 48–64 次二分；
4. 输出双精度利差与状态码。

二分法与 Brent 法的迭代轨迹不同，但该定价函数对利差严格单调。通过足够迭代次数可把绝对误差控制到远低于 CSV 保存精度，并与 CPU 结果建立明确容差。

## 分阶段实施记录

### 阶段 1：基准与接口

涉及文件：

- `backtest/market_data_contracts.py`
- `tests/test_market_data_contracts.py`

工作：

1. 将现有实现保留为明确的 CPU 基准函数；
2. 给公开入口增加 `backend="auto" | "cpu" | "cuda"`，默认 `auto`；
3. `auto` 在 CUDA 不可用或预检失败时回退 CPU，并明确打印原因；
4. 固化当前小样本结果和异常规则，防止 GPU 改造改变金融语义。

### 阶段 2：CPU 数值预处理

涉及文件：

- `backtest/market_data_contracts.py`
- 可选新增 `backtest/credit_spread_cuda.py`

工作：

1. 国债曲线只规范化和排序一次，不再为每个现金流复制整个 DataFrame；
2. 预先建立“估值日 → 最近合规曲线日”的映射；
3. 将债券静态条款解析为可复用结构；
4. 将有效债券日期问题和变长现金流压平为连续 `float64`/整数数组；
5. 保留每个问题的矩阵坐标和失败状态，确保无效单元仍输出 `NaN`。

这一阶段即使暂时使用 CPU 求根，也应显著减少重复 Pandas 与日期处理。

### 阶段 3：CUDA 求解器

建议新增：

- `backtest/credit_spread_cuda.py`

工作：

1. 实现独立、无 Pandas 依赖的 `@cuda.jit` 批量求根内核；
2. 使用 `float64` 保持与 CPU 定价一致；
3. 按问题数量分块传输，默认块大小根据显存动态计算；
4. CUDA 启动或执行失败时不吞错：`auto` 可回退 CPU，显式 `cuda` 模式则失败关闭；
5. 记录预处理、主机到设备传输、内核、设备到主机回传和总耗时。

### 阶段 4：检查点与原子写盘

涉及文件：

- `backtest/data_pipeline.py`
- GPU 模块或信用利差调度函数

工作：

1. 按债券批次计算并保存可恢复检查点；
2. 检查点包含输入日期范围、债券集合、代码版本和参数指纹，避免错误续跑；
3. 最终 CSV 先写临时文件，完成结构与覆盖率校验后再原子替换正式缓存；
4. 中断时保留最近完成批次，下次只处理未完成问题；
5. 正式缓存永远不暴露半写状态。

### 阶段 5：管线接入

涉及文件：

- `backtest/data_pipeline.py`
- `backtest/full_history_rebuild.py`
- 相关运行说明

工作：

1. 增加信用利差后端选择，例如 `--credit-spread-backend auto|cpu|cuda`；
2. 全量本地 RTX 5060 运行显式选择 `cuda`；
3. CI 或无 GPU 环境使用 `cpu`；
4. 日志打印设备名、问题数量、有效现金流数量、批次数、回退原因和耗时；
5. 不改变后续市值、评级、BPS、BS、ZL 的执行顺序。

## 验证门槛

实现按以下顺序验证；未通过时不得启动全量重跑。

1. 现有测试：运行信用利差和市场数据契约测试，确认 CPU 基准未回归。
2. 内核单元测试：覆盖零利差、正常求根、超过 5.0 上界、多现金流和无效输入。
3. CPU/GPU 一致性：固定小矩阵逐格比较，建议成功单元 `abs_error <= 1e-10`、状态码完全一致。
4. 随机样本：从现有缓存选择不同期限、票息、日期和曲线状态的样本，比较 CPU Brent 与 GPU 二分结果。
5. 小规模性能：只运行少量债券和日期，验证 GPU 加速、显存峰值与检查点恢复；不触发全历史管线。
6. 中断恢复：计算若干批次后主动停止，再次启动只能补算未完成批次。
7. 最终批准后才运行全量信用利差，并检查形状、日期范围、非空覆盖率、有限值和 CPU 抽样一致性。

## 风险与控制

- **双精度吞吐量**：消费级 RTX 的 FP64 性能有限。通过大量独立问题并行仍可能加速，但必须用小样本基准确认。
- **Compute Capability 12.0 兼容性**：设备已被 Numba 识别，但实施前仍需编译并运行最小 `float64` 内核，确认当前驱动、PTX 与 Numba 组合。
- **CPU 预处理仍可能成为瓶颈**：若只把求根搬到 GPU，而保留双层 Pandas 循环，整体加速有限，因此阶段 2 是必要项。
- **Brent 与二分的末位差异**：用明确误差门槛和 CPU 抽样控制，不用逐位相等作为标准。
- **显存与变长现金流**：使用 CSR 数组和分块处理，禁止构造巨大的三维填充张量。
- **静默回退**：日志必须明确显示实际使用后端；显式 `cuda` 模式不得悄悄切换 CPU。
- **中断损失**：检查点和原子替换解决本次“运行一小时仍无落盘”的问题。

- `credit_spread_cuda.py` 已提供独立 CUDA 批量求根内核；
- `build_implied_credit_spread_matrix(..., backend="auto|cpu|cuda")` 已接入双后端；

- RTX 5060 Laptop GPU 的 CUDA 内核已实际运行验证。

后续性能目标仍需以真实增量批次持续校准：

- 信用利差阶段从当前超过 1 小时降到 5–15 分钟；
- 若 CPU 预处理充分向量化且 CUDA FP64 表现良好，争取 2–8 分钟；
- 即使 GPU 加速不及预期，也通过预处理和可恢复检查点避免再次整段损失。
